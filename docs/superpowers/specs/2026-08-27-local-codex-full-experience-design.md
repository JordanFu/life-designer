# 本地 Codex 完整体验设计

> 状态：已获用户授权直接实施，完成后统一验收  
> 日期：2026-08-27  
> 当前模式：Fork + 窄幅适配  
> 阶段预算：一个开发窗口；若本机 Codex 无法稳定返回结构化结果，或改动越过本地体验进入线上账号/计费，立即停止并重新确认

## 1. 执行契约

### 用户可见结果

用户在 `localhost` 完成四阶段人生设计时，不再只面对静态表单。每个关键节点都得到 Codex 基于本人原话生成的温暖承接、可验证洞察和一个具体追问。用户可以补充，也可以继续。全部素材齐全后，Codex 生成并展示可下载的《个人人生设计蓝图》。刷新或模型失败后，用户从准确断点继续。

### 规范参照

- 方法语义与语气以仓库 `SKILL.md` 和原始提示词为准。
- 检查点、恢复和四阶段状态机继续以 `packages/life-design-core` 为唯一业务真相。
- 本地模型调用遵循 OpenAI Codex CLI 的稳定非交互接口：`codex exec`、`--ephemeral`、`--sandbox read-only` 与 `--output-schema`。

### 必须匹配

- 四阶段仍为“你在这里、你的指南针、寻路、多种可能”。
- 模型不决定是否完成阶段；只有结构化状态机和用户动作可以推进。
- 三个奥德赛计划地位平等。
- AI 不做职业测评、心理诊断或替用户决策。
- 用户回答先落本地检查点，再发起模型请求。
- 模型失败、刷新或服务重启不能丢失已经填写的内容。

### 本轮允许改变

- 增加本地 Codex Provider 和 Next.js 服务端接口。
- 在现有步骤之间加入 AI 教练回应、补充回答和跳过动作。
- 将检查点迁移到新版本，保存 AI 回应、补充回答和蓝图。
- 完成蓝图展示、重新生成、Markdown 下载和浏览器打印。

### 非目标

- 公开部署、BYOK、项目方 API Key、支付、兑换码、账号和云端恢复。
- 把 Codex CLI 当作未来线上架构；它只是本地产品验收适配器。
- 无边界自由聊天、多 Agent、搜索或访问用户其他文件。

### 验收证据

真实运行一条黄金路径：

> 从新会话开始 → 第一阶段得到真实 Codex 回应 → 刷新后保持断点 → 完成四阶段并获得多次 AI 承接 → 生成蓝图 → 刷新后蓝图仍存在 → 下载 Markdown。

并证明模型失败时答案已保存且可重试，服务端没有向浏览器暴露 Codex 凭据。

## 2. 交互设计

### 2.1 主流程

基础问题仍采用“一屏一件事”的结构化引导。每当完成一个关键素材单元：

1. 本地保存用户原始回答。
2. 页面进入“教练正在读你的回答”状态。
3. 服务端调用本机 Codex，返回一段简短承接、一条洞察和一个具体追问。
4. 用户可填写补充回答，也可选择“先继续”。
5. AI 回应和补充答案保存成功后，状态机进入下一问题。

第一阶段九个微步骤合并为一个教练触点。后续工作观、人生观、能量地图、三个奥德赛计划和原型行动各形成一个触点。完整体验约产生七次模型调用（六次教练回应、一次蓝图）。

### 2.2 AI 教练卡

教练卡不是聊天气泡瀑布，只呈现当前需要理解的内容：

- “我听见了什么”：忠实复述，不套话。
- “这里可能值得看一眼”：标注为可能性，不做诊断。
- “只追问一件事”：具体、能从真实经历回答。
- 一个可选补充输入框。
- “补充并继续”“先继续”两个动作。

模型调用期间明确显示用户答案已经保存。失败时显示“回答已保存”，并提供“重试回应”和“先继续使用本地流程”。

### 2.3 蓝图

素材齐全后展示“生成我的人生设计蓝图”。生成结果至少覆盖：

1. 你在这里：四个仪表盘、失衡与被忽略处。
2. 真问题：重力问题、可设计问题和错误前提。
3. 指南针：工作观、人生观、一致与冲突。
4. 能量地图：心流、回血与消耗模式。
5. 三个平等的五年版本。
6. 当前优先原型：一个季度和一个月内的低成本行动。
7. 失败免疫与复盘提醒。

蓝图只引用检查点中的真实素材。信息不足时明确说不足，不虚构经历。结果保存到 IndexedDB，可重新生成、下载 Markdown，并使用浏览器打印为 PDF。

## 3. 技术设计

### 3.1 模块边界

```text
apps/web/app/api/codex/*       仅本地可用的服务端路由
apps/web/src/coach-*           教练卡、蓝图界面与客户端请求
packages/providers             Provider 接口、Codex CLI 适配器、Schema 与提示组装
packages/life-design-core      v4 检查点、迁移和状态转换
packages/checkpoint            IndexedDB 持久化，保持现有职责
```

Provider 不直接修改检查点。Core 不执行进程、不知道 Codex CLI。Web 负责“先保存—再调用—再保存结果”的编排。

### 3.2 检查点 v4

新增：

```ts
type CoachTurn = {
  id: string
  afterStepId: StepId | 'here.guided'
  acknowledgement: string
  insight: string
  followUp: string
  followUpAnswer?: string
  createdAt: string
}

type BlueprintState = {
  status: 'idle' | 'generating' | 'complete' | 'failed'
  markdown?: string
  generatedAt?: string
  error?: string
}
```

检查点同时记录等待生成教练回应的步骤标识。v3 会显式迁移到 v4，不删除任何原回答。

### 3.3 本地 Codex Provider

Next.js 服务端在独立临时目录中执行：

```text
codex exec --ephemeral --ignore-user-config --ignore-rules \
  --sandbox read-only --skip-git-repo-check \
  --output-schema <schema.json> --output-last-message <result.json> -
```

- Prompt 通过 stdin 传入，不拼接成 shell 命令。
- 使用参数数组启动子进程，避免 shell 注入。
- 临时目录只包含输出 Schema，不包含项目或用户其他文件。
- 120 秒超时，限制 stdout/stderr 大小，错误内容不回传敏感路径。
- 每次 `--ephemeral`，不保存 Codex rollout 会话。
- `--ignore-user-config` 仍保留 `CODEX_HOME` 认证，但不加载用户 MCP 和行为配置。
- 模型只获得本次所需的方法说明和结构化检查点，不获得浏览器数据、API Key 或其他本地文件。

### 3.4 API 数据流

`POST /api/codex/coach` 接收当前步骤、结构化检查点和可选补充回答，返回经 Zod 二次校验的 `CoachTurnDraft`。

`POST /api/codex/blueprint` 接收完整检查点，返回经校验的标题和 Markdown。

请求体限制大小。路由只允许开发/本机环境调用；生产模式若未显式启用本地 Codex 则返回不可用，防止误部署后执行宿主机命令。

## 4. 错误与恢复

| 场景 | 用户结果 | 状态处理 |
|---|---|---|
| Codex 未登录/不可用 | 回答已保存，可重试或跳过 | 保留等待教练回应的步骤 |
| 调用超时 | 显示超时，不重复提交答案 | 可重试同一模型操作 |
| JSON 不合法 | 不展示半截回应 | Provider 校验失败，保留断点 |
| 刷新发生在模型调用中 | 回到等待教练回应状态 | 不假装调用仍在进行，允许重新生成 |
| 蓝图生成失败 | 所有四阶段素材仍可导出 | 仅蓝图标记 failed，可单独重试 |
| 用户重新生成蓝图 | 原蓝图在新结果成功前仍保留 | 成功后原子替换 |

## 5. 测试

- Provider 单元测试：成功、超时、非零退出、无效 JSON、Schema 不匹配和命令参数安全。
- Core 单元测试：v3→v4 迁移、教练等待态、保存回应、补充/跳过、蓝图成功/失败。
- Web 组件测试：保存先于请求、失败不推进、重试不重复回答、蓝图下载无凭据。
- API 路由测试：请求限制、开发环境门禁、错误映射。
- Playwright：用可控 fake provider 跑完整自动化；再用真实本机 Codex 手工跑一条黄金路径。
- 手机视口检查：加载、教练卡、失败态、蓝图阅读均无横向溢出。

## 6. 完成定义与停止条件

达到以下条件才称为“可验收”：

- 本地真实 Codex 至少成功产生一条教练回应和一份蓝图。
- 自动化测试、类型检查和生产构建通过。
- 刷新恢复、失败重试和 Markdown 下载可见验证通过。
- 页面明确说明内容会发送给当前本机登录的 Codex 服务。

若 `codex exec` 的真实延迟或稳定性不足以支撑逐节点体验，则保留相同 Provider 接口，将调用降为每阶段一次；不得为了维持调用次数牺牲流程可用性。
