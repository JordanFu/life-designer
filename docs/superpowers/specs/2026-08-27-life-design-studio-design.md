# Life Design Studio 产品与技术设计

> 状态：ready for acceptance  
> 日期：2026-08-27  
> 当前模式：**Fork + 窄幅适配**，不是独立重建

## 1. 执行契约

### 用户可见结果

做一个免费开源、移动端优先的 Web/PWA。用户通过 30–60 分钟、可分多次完成的四阶段对话，获得自己的《个人人生设计蓝图》，并可下载 Markdown、可打印 HTML/PDF 和供其他 AI Agent 继续使用的交接包。

体验提供两种入口：

1. **自带 Key（BYOK）**：免费使用，Key 默认只保留在当前浏览器会话中。
2. **托管体验**：使用项目方的模型额度，按次付费，以覆盖模型、支付和基础设施成本为主。

### 规范参照

- 方法、对话语气、四阶段语义、报告结构：`Jackychen-12/life-designer`（MIT）。
- 跨会话进度文件思路：`TeigenZhang/life-design-coach`（MIT）。
- 消息持久化、失败恢复和可恢复流式响应模式：参考 `vercel/ai-chatbot`（Apache-2.0），不复制其整套产品。
- 本项目保留上游版权和许可证，并在 README 中明确说明改造来源。

### 必须保持的语义

- 四阶段依次覆盖“你在这里、你的指南针、寻路、多种可能”。
- 先区分无法改变的重力问题与可设计的真问题。
- 三个五年版本地位平等，不能把其中两个写成陪衬。
- 对话温暖但不替用户决定，不做职业测评、医疗诊断或心理治疗。
- 一次只聚焦一个主问题，允许有深度但不能把流程拖成无边界闲聊。
- 蓝图必须以用户真实表达为证据，不能用套话补齐字数。

### 允许改变

- 将原 Agent/CLI 体验扩展为 PWA。
- 增加结构化检查点、自动保存、匿名恢复链接、BYOK、托管计费和多格式导出。
- 在不改变四阶段含义的前提下，调整界面顺序、提示文案和问题数量。
- 将报告改为分章节生成，以降低长任务中断风险。

### 本期非目标

- 微信小程序、原生 App、社区、公开分享、排行榜。
- 企业版、员工画像、管理看板、组织分析或任何隐性数据采集。
- 通用聊天平台、多 Agent 编排、知识库、模型市场。
- 注册体系、长期云端聊天记录、订阅制和复杂优惠体系。

### 验收证据

必须演示一条真实黄金路径：

> 开始对话 → 回答至少 3 个问题 → 关闭页面 → 恢复到准确断点 → 完成四阶段 → 报告生成中刷新 → 继续缺失章节 → 导出蓝图与 Agent 交接包。

除可见流程外，还需证明：Key 不写入检查点或日志；恢复链接过期有效；相同操作重试不会重复扣减使用次数；删除本地和云端数据确实生效。

## 2. 产品体验

### 2.1 进入体验

首页只做三件事：说明这是一次什么体验、预计用时和可随时暂停；展示 BYOK 与托管体验两个入口；明确“你不需要先想清楚自己热爱什么”。

进入后先选择：

- **免费 · 使用自己的 API Key**：选择兼容的模型服务，粘贴 Key，完成一次连通性测试。Key 默认进入 `sessionStorage`，不写入 IndexedDB、恢复包、分析日志或服务端数据库。用户重新打开浏览器时可能需要再次输入 Key。
- **省心 · 托管体验**：购买或兑换一次体验券。服务端只返回有次数和有效期限制的会话令牌，不向前端暴露项目方 API Key。

不要在用户尚未理解产品价值时要求注册、付费或填写大量资料。

### 2.2 四阶段对话

界面以单问题对话为主，顶部只显示四段进度，不显示“剩余 47 个问题”之类制造压力的数字。

每次回答后的顺序固定为：

1. 立即将用户原文写入本地检查点。
2. 更新结构化摘要与当前阶段状态。
3. 调用模型生成简短回应和下一个主问题。
4. 完整响应校验后再把问题游标向前移动。

用户随时可以选择“先到这里”。系统保存断点，并生成一句不带评判的阶段小结。

### 2.3 恢复体验

重新进入时不要求用户重述情绪或重新走已完成问题。恢复页显示：

- 上次停留时间与阶段；
- 3–5 句“我们已经知道什么”；
- 上次完整保存的回答；
- 当前唯一要继续的问题；
- “继续”“回看”“换一个问题”三个动作。

如果模型响应中途断开，用户回答仍然安全保存。系统提示“你的回答已保存”，并允许重新生成回应；不能让用户猜测究竟是否保存成功。

### 2.4 输出与继续使用

完成后提供：

- `人生设计蓝图.md`：便于复制和长期维护。
- `人生设计蓝图.html`：带打印样式，可由浏览器保存为 PDF。
- `life-design-checkpoint.json`：结构化、版本化的进度数据。
- `life-design-agent-pack.zip`：包含 `README.md`、`context.md`、`checkpoint.json` 及兼容 Agent 的继续对话说明。

蓝图按章节逐一生成和保存。刷新页面后只生成缺失或失败的章节，不重新消耗已成功章节的额度。

## 3. 信息架构

移动端主导航只保留：

- **对话**：当前问题、输入区、阶段进度。
- **地图**：四个仪表盘、真问题、指南针、能量模式、三个奥德赛计划的逐步成形结果。
- **蓝图**：完成前显示章节准备状态，完成后显示报告与导出。

设置通过对话页菜单进入，包含模型连接、恢复与导入、隐私和删除。桌面端可将“地图”作为右侧可折叠栏；移动端不并排展示，避免输入区域过窄。

## 4. 技术架构

### 4.1 代码边界

建议在现有仓库中形成四个清晰模块：

```text
apps/web                 PWA、对话界面、地图、蓝图和导出
packages/life-design-core 四阶段状态机、Schema、提示组装和安全规则
packages/checkpoint       本地/云端检查点、迁移、加密与恢复
packages/providers        BYOK 与托管模型的统一流式接口
```

保留上游 `SKILL.md`、Python 报告生成器和参考资料，先保证原 Agent 用法仍可运行；Web 逐步调用同一份版本化方法配置，避免 CLI 与 Web 各自演化出两套人生设计语义。

首选实现栈：TypeScript、Next.js App Router、React、IndexedDB（Dexie）、Zod、Web Crypto、Playwright。部署目标保持可替换，不能把核心流程绑死在单一云厂商。

### 4.2 会话检查点

检查点是产品的源数据，聊天文本只是它的一种呈现。最低结构如下：

```ts
type LifeDesignCheckpoint = {
  schemaVersion: number
  sessionId: string
  revision: number
  createdAt: string
  updatedAt: string
  mode: 'byok' | 'hosted'
  stage: 'here' | 'compass' | 'wayfinding' | 'odyssey' | 'report'
  currentQuestion: { id: string; text: string } | null
  completedQuestionIds: string[]
  answers: AnswerRecord[]
  stageSummaries: Record<string, string>
  gravityProblems: ProblemRecord[]
  designableProblems: ProblemRecord[]
  dashboards: DashboardScores
  compass: CompassState
  energyMap: EnergyEvent[]
  odysseyPlans: OdysseyPlan[]
  reportSections: ReportSectionState[]
  pendingOperation: PendingOperation | null
  usage: { inputTokens: number; outputTokens: number; hostedUnits: number }
}
```

每次变更增加 `revision`，并通过 Zod 验证。将来结构变化必须提供显式迁移；不允许静默丢字段。

### 4.3 本地与云端恢复

**开源/BYOK 默认路径**：

- 每次回答先写 IndexedDB，再发模型请求。
- 使用事务同时保存答案、游标和 `pendingOperation`。
- 页面关闭前不依赖 `beforeunload` 才保存；它只做最后提示。
- 用户可随时导出检查点并在另一台设备导入。

**托管体验路径**：

- 本地仍是即时主副本；云端保存 30 天匿名加密快照，用于跨设备恢复。
- 浏览器使用 Web Crypto 生成密钥并加密，服务端只保存密文、版本、过期时间和必要的用量状态。
- 完整恢复链接中的密钥放在 URL fragment，不随 HTTP 请求发送给服务器。
- 用户可主动删除；到期自动删除。恢复短码若进入后续版本，必须结合用户持有的秘密或口令，不能用可枚举的短码直接解密。

### 4.4 模型调用

`ModelProvider` 统一返回流式事件、用量和结构化结果：

```ts
interface ModelProvider {
  testConnection(): Promise<ConnectionResult>
  continueConversation(input: TurnInput): AsyncIterable<ModelEvent>
  generateReportSection(input: ReportSectionInput): AsyncIterable<ModelEvent>
}
```

- BYOK Provider 使用用户选择的兼容接口；密钥只存在当前浏览器会话或当前自托管服务进程。
- Hosted Provider 通过服务端代理，使用短期会话令牌、每操作幂等键、速率限制和用量上限。
- 上下文由“方法指令 + 结构化检查点摘要 + 最近必要轮次”组成，避免每次发送全部历史。
- 任何模型都不能直接决定阶段已完成；状态机依据结构化结果和用户动作推进。

### 4.5 报告生成

报告拆分成独立章节任务，每个任务有 `pending/generating/complete/failed` 状态、内容哈希和幂等键。章节完成立即写本地；托管模式同时上传加密快照。

生成 8000–12000 字是质量目标而非硬凑字数。若素材不足，系统应补问 1–2 个关键问题或生成更短但诚实的蓝图，不能虚构用户经历。

## 5. 隐私、安全与伦理边界

- 私人内容默认不公开、不用于训练、不进入组织或员工分析。
- 不采集联系人、位置、相册、其他聊天记录等与人生设计无关的数据。
- 分析数据默认只记录无内容事件，例如阶段完成、错误类型和耗时；不得记录答案正文、提示词、API Key 或完整恢复链接。
- 用户可在设置页看见数据在哪里、何时过期、如何导出和删除。
- 托管模型供应商的数据处理边界必须在付款前说明，不能承诺项目无法验证的“绝对零留存”。
- 发现自伤或紧急危险表达时，暂停普通教练流程，提供明确、尊重且本地化的求助建议；本产品不冒充危机干预服务。
- API Key 输入框默认隐藏，日志与错误上报必须做密钥模式脱敏。

## 6. 付费与成本控制

开源能力不做人为阉割：自托管、BYOK、导入导出和完整四阶段流程均免费。付费购买的是“无需配置 Key 的托管便利”，不是用户对自己数据的访问权。

MVP 使用一次性体验券/兑换码模型：

- 每张券绑定一次完整会话的用量上限和有效期。
- 对话与报告分别计量，但对用户展示“本次体验是否足够完成”，不展示复杂 Token 账单。
- 所有重试使用幂等键；网络错误不重复扣体验次数。
- 接近预算时优先压缩历史上下文、使用便宜模型做摘要，不降低关键反思与最终蓝图的质量。

支付模块定义抽象接口。首轮内测可以先用人工发放兑换码验证真实完成率，再接支付渠道，避免在尚未验证体验前建设复杂计费系统。

## 7. 错误处理

| 场景 | 用户看到的结果 | 系统行为 |
|---|---|---|
| 模型连接失败 | 清楚说明回答已保存，可重试或更换模型 | 保留 `pendingOperation`，不移动问题游标 |
| 页面刷新/崩溃 | 返回上次完整保存的问题与回答 | 从 IndexedDB 最新合法 revision 恢复 |
| 云端快照冲突 | 提示本机与云端更新时间，默认保留两份 | 不静默覆盖，支持复制会话 |
| 检查点版本过旧 | 先备份原文件，再尝试迁移 | 迁移失败时只读打开并提供导出 |
| 报告某章失败 | 其他已完成章节可读，只重试失败章节 | 用章节幂等键和哈希去重 |
| 托管额度不足 | 不丢失对话，可导出或切换 BYOK | 冻结新的托管调用，不锁住用户数据 |
| 恢复链接过期 | 解释过期，不泄露是否存在某个会话 | 返回统一错误，可从本机/导出包恢复 |

## 8. 测试策略

### 技术正确性

- Core：状态迁移、问题游标、重力/真问题分类、三个计划的平等性校验。
- Checkpoint：事务写入、Schema 迁移、并发 revision、加解密、过期与删除。
- Provider：断流、超时、限流、无效 Key、幂等重试和 Token 统计。
- Export：Markdown/HTML/JSON/ZIP 内容完整、无 Key、可重新导入。

### 产品正确性

- 用一份真实但去标识化的完整对话，逐阶段比较上游方法语义和新 Web 结果。
- 检查恢复摘要是否忠于用户表达，是否把不可改变的现实误写为待解决任务。
- 检查三个五年计划是否均为真心可选的 A 计划。
- 在手机默认视口进行逐屏视觉检查，不以单元测试代替实际体验。

### 端到端黄金路径

Playwright 覆盖：BYOK 进入、回答保存、强制关页、恢复、断流重试、四阶段完成、报告中刷新、章节续生成、导出、删除。托管路径另外覆盖兑换、额度、幂等与 30 天恢复链接。

## 9. 分阶段交付与停止条件

### 阶段 0：语义与恢复纵切片（预算：1 个开发窗口）

只实现“进入 → 回答 3 题 → 关页 → 准确恢复 → 导出检查点”。不做付款和完整报告。

停止条件：无法在不改动上游核心语义的情况下形成合法检查点；或刷新后仍需用户重述答案。

### 阶段 1：完整 BYOK PWA（预算：2–3 个开发窗口）

完成四阶段、地图、分章蓝图、Markdown/HTML/Agent 包导出，以及安装为 PWA。

停止条件：黄金路径不能稳定跑通；实际手机界面不可用；报告依赖虚构内容才能达标。

### 阶段 2：小规模托管体验（预算：1–2 个开发窗口）

加入匿名加密恢复、兑换码、服务端模型代理、用量上限和删除。先开放少量免费体验名额，测量完成率、平均消耗和恢复率。

停止条件：单次真实成本超过估算 2 倍；隐私边界无法解释清楚；重试导致重复计费。

### 阶段 3：支付与公开发布

只有阶段 2 证明用户愿意完成全流程、成本可控后才接支付。微信小程序是否需要，依据真实设备和渠道数据再决定。

- 现有报告结构移植到 Web 后是否仍能保持语气和深度。
